# 48/96 — Build Plan

A pay calculator for the shift, built from the FY pay calendar workbook. Runs on
a phone, stores nothing off-device, and tells you which line of your check is wrong.

- **Platform:** installable web app (PWA)
- **Storage:** on-device only (localStorage)
- **Backend:** none
- **Hosting:** GitHub Pages, $0
- **Effort:** ~7–8 working sessions

> This describes an unofficial tool for personal comparison. It is not a payroll
> record and carries no authority in a pay dispute.

---

## 1. What we're building

The workbook already contains the hard part: the department's actual pay rules,
encoded as formulas. This project lifts those rules into code, wraps them in
something operable one-handed, and adds the thing a spreadsheet can't do well —
tell you *which line* of your check is wrong.

Four properties drive every decision:

- **No server, no accounts.** Rate, certs, and hours are compensation data. It
  stays on the device.
- **No app store.** Share a link, tap "Add to Home Screen."
- **The year is data, not code.** Calendar, holidays, incentive tables, and the
  FLSA threshold live in a swappable file.
- **Every number is traceable.** The engine returns an itemized breakdown, not a
  total.

"48/96" is a placeholder name.

## 2. The two-year problem

FY26 (supplied later) ships as the live year so people can check real checks
immediately. FY27 — already decoded from the supplied workbook — sits alongside
it and takes over on 2026-09-26 automatically, with no update or re-install.

Each year file declares `effectiveFrom` / `effectiveTo`; the app selects the year
whose window contains today. A year picker allows auditing a closed year, which
matters because payroll errors get noticed months late.

## 3. Architecture

| Layer | Responsibility |
|---|---|
| **Year data** | Calendar, pay periods, holidays per shift, incentive tables, step-up rates, FLSA threshold, raise rules. One JSON file per fiscal year, generated by an importer script. |
| **Engine** | Pure functions. Year file + profile + hours → itemized result. No UI, no storage, no system clock. |
| **Storage** | Versioned localStorage wrapper for profile and hours, plus export/import. Never transmits. |
| **Interface** | Mobile-first screens. Renders engine output; contains zero pay math. |

**Stack:** TypeScript, React, Vite, Vitest, Tailwind, `vite-plugin-pwa`. Static
build to GitHub Pages. Importer is a Node script (`exceljs`), run manually once a
year — not part of the shipped app.

**Hard rule:** the UI never does arithmetic. If a number appears on screen, the
engine produced it and a test covers it.

## 4. The year file

```jsonc
{
  "id": "FY27",
  "label": "FY 2027",
  "effectiveFrom": "2026-09-26",
  "effectiveTo":   "2027-09-24",

  "periodLengthDays": 14,
  "flsaThresholdHours": 106,     // 7(k) fire, 14-day
  "longevityDivisor": 2912,

  "shifts": {
    "A": { "cycleAnchor": "2026-09-27", "pattern": [24,24,0,0,0,0] },
    "B": { "cycleAnchor": "2026-09-29", "pattern": [24,24,0,0,0,0] },
    "C": { "cycleAnchor": "2026-09-26", "pattern": [24,24,0,0,0,0] }
  },

  "periods": [ { "n": 1, "start": "2026-09-26", "end": "2026-10-09" } ],

  "holidays": [
    { "date": "2026-11-26", "name": "Thanksgiving", "hours": 12 }
  ],

  "incentives": {
    "tcfp":       { "Intermediate": 0.2061, "Advanced": 0.4121, "Master": 0.6181 },
    "education":  { "Associate": 0.4121, "Bachelor": 0.6181,
                    "Master": 0.8242, "PhD": 1.0302 },
    "emt":        { "AEMT": 0.625, "Paramedic": 2.0604 },
    "bilingual":  0.3091,
    "assignment": { "QA/QI": 1.10 }
  },

  "stepUpRates": { "F2": 35.3302, "F3": 41.7567, "F4": 48.8774 },

  "raise": { "pct": 3.0, "trigger": "anniversary", "proration": "TBD" }
}
```

`raise.proration` is the one field that can't be filled in yet. The sheet applies
the 3% to an entire pay period based on that period's *start* date, so a period
straddling the anniversary pays the new rate on all 120 hours. Real payroll
usually splits the period or starts the raise the following period. A paystub
from the period containing the anniversary settles it.

The importer extracts holiday *dates* rather than trusting the sheet's hand-wired
per-shift holiday formulas, then prints a table for human confirmation against the
department calendar. One deliberate human check per year.

## 5. Verification — two ladders

### Rung one: parity with the sheet

Harness reads the workbook's computed values and asserts the engine reproduces
them — 26 periods × 3 shifts, to the cent, at the sheet's own inputs. Deliberate
differences live in a `KNOWN_DIVERGENCES` table with a written reason; the test
asserts each divergence is exactly the expected amount.

Proves: the port is faithful. Does *not* prove: the rules are right.

### Rung two: parity with paystubs

Real stubs are the only ground truth. Each becomes an anonymized fixture. The
harness prints a line-by-line delta per stub.

**Reading a mismatch correctly:**

- A **consistent** disagreement across many stubs → *our model is wrong.* Fix the engine.
- A **one-off** disagreement, where the same rule paid correctly elsewhere → *the check is wrong.* That's the bug the tool exists to catch.

Volume matters more than perfection; a handful of stubs can't distinguish these.

### What each stub settles

| Open question | Stub that answers it | Priority |
|---|---|---|
| Is the **top-out bonus** in the FLSA regular rate? Sheet has the field, no formula reads it. | A period with OT while a top-out bonus was on file | High |
| **Anniversary raise** — split mid-period or start next period? | The period containing the anniversary date | High |
| Is **longevity** really folded in at ÷2912? | A period with OT while drawing longevity | High |
| Does **PTO** stay out of the OT count? | A period over 106 hrs including vacation or sick | Medium |
| Does the **step-up blended rate** match payroll's? | A period mixing regular and step-up hours, over 106 | Medium |
| **Holiday worked** at exactly 12 hrs — sheet returns 0 on one row | Any stub with partial holiday hours worked | Low |

## 6. Paystub handling

**Redact before sending:** name, employee ID, SSN digits, home address, bank and
routing numbers, YTD block if preferred. None of it is needed.

**What the harness needs:** pay period start/end dates, each pay code with hours,
rate, and amount, and the member's rate/certs/longevity as of that period.

**Where it lives:** raw stub files are excluded from git via `.gitignore`.
Committed fixtures carry numbers only — no names, no IDs, shift letters swapped
where it doesn't affect the math. A repo reader learns the department's pay rules
and nothing about any individual.

The same rule applies to coworker-contributed stubs, and should be stated up front
when asking.

## 7. Phases

Each phase has a **gate** — a condition that must be demonstrably true before the
next begins.

### 00 — Scaffold (~½ session)
Vite + React + TypeScript + Tailwind + Vitest. Strict TS, lint, format, CI on
push. GitHub Pages deploy wired up.

> **Gate:** a placeholder page is live at a phone-openable URL and CI is green.

### 01 — Year file + importer (~1 session) · *needs FY26 sheet*
Define and type the `PayYear` schema with a runtime validator so a malformed year
file fails loudly. Build `npm run import-year -- FY27.xlsx`. Emit and hand-verify
`fy27.json`. Repeat for FY26 on arrival.

> **Gate:** both year files validate; period boundaries, holiday dates, and rate
> tables match the source workbooks field for field.

### 02 — Pay engine (~1 session)
Pure functions, no UI, no side effects:

- `buildSchedule(year, shift)` — 48/96 rotation expanded to real dates
- `effectiveRate(profile, date)` — base + incentives, anniversary raise applied
- `computePeriod(...)` — straight, holiday off, holiday worked, OT hours, FLSA premium, gross
- `computeStepUp(...)` — weighted regular rate for mixed regular / step-up / TIFMAS

Every function returns labeled line items with the inputs used, not just a total.

> **Gate:** full branch coverage including zero-hour periods, PTO exceeding the
> threshold, and a period straddling the anniversary.

### 03 — Sheet-parity harness (~½ session)
Extract the workbook's computed values for 26 periods × 3 shifts, assert to the
cent, and write the `KNOWN_DIVERGENCES` table naming each sheet bug, the correct
behavior, and the expected dollar difference.

> **Gate:** 78 period comparisons pass; every divergence is intentional,
> documented, and asserted.

### 04 — Storage (~½ session)
Versioned localStorage schema with a migration path. File export/import. Graceful
behavior when storage is blocked or full.

> **Gate:** export from one browser, import into another, identical numbers.

### 05 — Interface (~2–3 sessions)

- **Setup** (once) — shift letter, hourly rate, cert pickers that compute the incentive rate, longevity, top-out, anniversary date
- **This period** (home) — 24s pre-filled from the deterministic rotation; only exceptions get touched (PTO by type, trade, OT shift, holiday worked). Gross at bottom, itemized on tap
- **Year** — 26 periods, running total, year picker for closed years
- **Step-up & TIFMAS** — entered as pay codes on the period screen so the blended FLSA rate happens automatically
- **Compare to check** — enter what the check paid, get the delta by line: not "you're short $187.72" but "your FLSA premium is missing $187.72"
- **Settings** — export, wipe, active year, disclaimer

> **Gate:** a real period entered from memory on a phone, under a minute, without
> instructions.

### 06 — Paystub harness (~½ session, then ongoing) · *needs stubs*
Fixture format and anonymizing intake per §6. Delta report per stub. Triage each
mismatch as engine bug, inherited sheet bug, or payroll error. Resolve the six
open questions and delete the guesses from the year file.

> **Gate:** every stub either matches or has a written explanation of the
> disagreement.

### 07 — Cutover & ship (~½ session)
Date-based year resolution with a clock-faking test across the 2026-09-26
boundary. iOS/Android install instructions as a first-run card. Crew-facing "how
to use this" page. Offline cold-start check.

> **Gate:** installed on a fresh phone, in airplane mode, producing correct numbers.

sheet already in hand.

## 9. Risks

| Risk | Mitigation |
|---|---|
| **The sheet's rules are wrong** — one person's reverse-engineering, never validated against a check | The paystub ladder exists for this. Until stubs land, the engine is a faithful port of a hypothesis, and the app should say so |
| **Pay rules change mid-year** — settlement, new incentive, rate revision | Year files can carry dated overrides. A day if it happens, nothing to design for now |
| **localStorage cleared**, a year of entries lost | Export/import in Phase 04, surfaced not buried, plus a periodic backup nudge |
| **People trust it too much** and treat it as evidence in a pay dispute | Persistent framing: an estimate for comparison. Its job is to tell you to go *ask* |
| **Annual update falls to one person** and the tool dies | Importer plus a written runbook: a documented 30-minute job, not tribal knowledge |

## 10. Sequencing

Phases 02 and 03 are the only genuinely uncertain part of the build; everything
after is ordinary app construction. They go first, before any screen is designed,
proven against FY27 while FY26 is pending.

**First milestone: 00 → 03.** A live URL, a tested engine, and a passing 78-period
parity report — roughly two and a half sessions in, with no UI. That's the
checkpoint to put in front of the sheet's author. If he can break it, better then
than after a UI is built on top.

## Appendix — pay model decoded from FY27

**Schedule:** 48/96, 6-day cycle. FY27 starts Sat 2026-09-26. A/B/C offset 2 days
each. A-shift 2,928 hrs/yr; B and C 2,904.

**Pay period:** 14 days, FLSA 7(k) threshold 106 hrs. Periods alternate 120 / 96
hours worked.

| Component | Formula |
|---|---|
| Effective rate | `hourly + incentive_total` |
| Straight pay | `total_hrs × eff_rate` (PTO included) |
| Holiday off (HO) | `HO_hrs × eff_rate` |
| Holiday worked (HW) | `HW_hrs × eff_rate × 1.5` |
| OT hours | `max(0, total_hrs − PTO − 106)` |
| FLSA premium | `OT × 0.5 × eff_rate + (longevity ÷ 2912 × OT × 0.5)` |
| Anniversary raise | after anniversary date, rate becomes `hourly × 1.03` |

Correct in the sheet and worth preserving: PTO is paid but excluded from the FLSA
OT count, and the incentive is folded into the regular rate before OT is figured.

### Known defects in the source workbook

1. **Top-out bonus is dead.** Entered in `O3` on each shift tab, formatted as an
   input, referenced by zero formulas. The Step-up tab's equivalent (`B20`) *is*
   wired in, so the intent is clear — the calendars were never hooked up.
2. **Holiday rows disagree with each other.** `K17` branches on `<12` and `>12`
   with no case for exactly 12, returning 0 holiday-worked hours. `K23` uses `>=12`
   and handles it correctly.
3. **`IF(K17<24>=0, …)`** — a chained comparison Excel always evaluates as TRUE.
   Correct for current values by luck only.
4. **Anniversary raise applies to a whole period** based on its start date.
5. **Holiday rows are hand-wired** per shift per holiday (rows 17, 23, 29, 41, 57,
   65, 77), each with bespoke formulas against specific day columns. Correct as
   built for FY27; the most fragile part for next year's rebuild.
